Required changes:

1. Do not block token discovery on getTokenLargestAccounts.
A newly decoded token must immediately be stored, evaluated with available data, published, and shown in the candidate feed even if holder data is unavailable.

2. Split enrichment into two phases.

Phase A — immediate:
- getTokenSupply
- getAccountInfo for bonding curve
- decodeCurve
- store token
- evaluateAll
- publish
- mark the signature processed

Phase B — delayed holder enrichment:
- getTokenLargestAccounts
- calculate Top 10
- update holderFresh
- evaluateAll again
- publish updated token

3. Add a dedicated holder enrichment queue:
- HOLDER_RPC_MAX_CONCURRENCY default 1
- HOLDER_QUEUE_MAX default 250
- HOLDER_INITIAL_DELAY_MS default 15000
- HOLDER_RETRY_DELAY_MS default 60000
- HOLDER_MAX_RETRIES default 5

4. On getTokenLargestAccounts rate limit:
- do not keep the main signature worker busy
- requeue the mint for a later holder lookup
- use Retry-After when available
- otherwise wait at least 60 seconds
- do not count the entire token scan as failed

5. Prevent duplicate holder jobs:
- one pending/in-flight job per mint
- successful holder enrichment removes the mint from the queue

6. Holder data behavior:
- holderFresh:false until getTokenLargestAccounts succeeds
- holderCount:null while unavailable
- top10Pct:null while unavailable
- UI/API should display unavailable values as “—”
- the token must still appear in decisions
